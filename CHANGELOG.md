## [Unreleased]

### Added

- **`InferenceEndpointModel` accepts a UC-securable model name, optionally qualified by a `schema:` anchor.** The Unity AI Gateway addresses models as UC securables, so a model id can be a three-level name (`system.ai.claude-sonnet-4-5`) rather than a serving endpoint name (`databricks-claude-sonnet-4-5`) — and there was no way to say that with a `SchemaModel`, even though `TableModel`, `VolumeModel`, `FunctionModel` and every other UC-backed config class already spell it the same way. The class now implements `HasFullName`, and `full_name` resolves `<catalog>.<schema>.<name>` when `schema` is set. **All three spellings work, and the first two are byte-for-byte what they were before:** a plain endpoint name (`name: databricks-claude-sonnet-4-5`) is used verbatim, an already-qualified `name: system.ai.claude-sonnet-4-5` is used verbatim, and `schema: *system_ai` + `name: claude-sonnet-4-5` resolves to the same qualified id — so one anchor can be reused instead of repeating `system.ai.` on every model. The field is spelled `schema:` in YAML via `Field(alias="schema")` (the attribute is `schema_model` only because `schema` shadows a pydantic method), matching how the same key is declared on every sibling class; the deploy bake already dumps `by_alias=True`, so it round-trips.

  Two combinations are rejected at config load rather than left to fail as an opaque 404 on first invocation. **A UC-securable name requires `use_ai_gateway: true`**, because a three-level name is only addressable on the gateway — verified live on a workspace: the same id answers `200` on `/ai-gateway/mlflow/v1/chat/completions` and `404 ENDPOINT_NOT_FOUND` on `POST /serving-endpoints/system.ai.claude-sonnet-4-5/invocations`, and `serving_endpoints.get()` raises `ResourceDoesNotExist` for it. The check keys on the resolved `full_name`, so both spellings that produce one are covered — a `schema:` anchor and a dotted `name:` alike; keying it on `schema` alone would have rejected one spelling while waving the equivalent one through to the 404 the check exists to prevent. And **`schema` alongside an already-qualified `name` is rejected**, since concatenating would yield `system.ai.system.ai.claude-sonnet-4-5`; `VolumeModel` and `EvaluationDatasetModel` both carry that latent bug and this class does not inherit it.

  Two consequences for a model whose `full_name` is three-level. `as_resources()` emits **nothing** instead of a `DatabricksServingEndpoint`: MLflow has no resource type for a UC-securable model, and the platform resolves `endpoint_name` against `/api/2.0/serving-endpoints`, where neither the qualified nor the short name exists — so either spelling would have put an unresolvable name into the deploy manifest and auth policy. Access is governed by UC grants on the model instead (grant the deploying service principal `EXECUTE`), and the gateway's OBO `ai-gateway` scope is emitted separately as before. And `uri` (which feeds MLflow judges and scorers) now reports `databricks:/<full_name>` rather than `databricks:/<name>`, so a schema-qualified judge model names the model it actually means. **Models addressed by endpoint name are untouched on both counts** — no `schema`, no dots, identical resource and identical `uri`. Serving endpoint names cannot contain dots, so the "three-level `full_name`" test cannot misfire on an existing config.

  **A UC-securable model works on Databricks Apps but not on Model Serving**, and the reason is the paragraph above meeting Model Serving's automatic authentication. Both targets were deployed live from one config carrying workers on all three spellings: on Apps every worker answered `200`; on Model Serving the two `databricks-*` workers answered `200` while all three UC-securable ones failed with `404 "'system.ai.claude-sonnet-4-5' does not exist."` — a model whose id answers `200` under a full-scope token on the same workspace, and which resolves to the identical provider model as its `databricks-*` twin. The endpoint's token is downscoped to exactly the resources in the logged auth policy (confirmed on the artifact: only the two serving endpoints, `user_auth_policy.api_scopes: []`), and a UC-securable model can declare none, so it is invisible to that token and the gateway reports the absence as `NOT_FOUND`. Apps is unaffected because its service principal holds a workspace identity of its own. dao-ai now emits a **warning at deploy time** naming each affected model and both ways out — use the serving-endpoint spelling, or `on_behalf_of_user: true` to have the user's forwarded token used instead — so this surfaces while an operator can still act, rather than as a runtime 404 that names a model which demonstrably exists.

### Changed

- **BREAKING (Python API only) — `InferenceEndpointModel.ai_gateway` is renamed `use_ai_gateway`.** dao-ai was the only layer in the stack that spelled this flag differently: `use_ai_gateway` is the `databricks-langchain` kwarg the field feeds, and it is already the field name on `ChatUnityAIGateway` — so a reader tracing the value from YAML to the wire had to notice it changed names once, in the middle, for no reason. **YAML configs need no edits**: `ai_gateway:` still parses via a `validation_alias`, chosen over `Field(alias=...)` precisely because `alias` would flip the *canonical* schema name to the legacy spelling and defeat the rename for editors and the checked-in JSON schema (the same reasoning as `ResourcesModel.models` accepting legacy `llms`). What does break is Python code reading the attribute — `model.ai_gateway` is now an `AttributeError`, so use `model.use_ai_gateway`. The legacy key will be removed in a future major release. The default is **unchanged at `false`**: flipping it would have silently re-routed every one of the ~40 `InferenceEndpointModel` constructions that rely on the implicit default and added an `ai-gateway` OBO scope to embedding models, so the rename carries no runtime effect on its own.
- **`use_ai_gateway: true` now composes with `use_responses_api: true`** instead of raising at config load. `_validate_ai_gateway_compatibility` rejected the pair on the premise that the gateway was OpenAI-compatible chat-completions *only*; that is false. `/ai-gateway/mlflow/v1` serves both `/chat/completions` and `/responses`, and raw HTTP against a live workspace answers `200` on **both** paths for every model tried — `gpt-5-4`, `gpt-5-4-mini`, `gpt-5-mini`, `gpt-oss-120b`, `claude-sonnet-4-5`, and `system.ai.*` spellings alike. Nothing in `databricks-langchain` or `databricks-openai` blocked the combination either: `use_responses_api=True` makes `ChatDatabricks` call `client.responses.create`, and where that lands is decided purely by the client's `base_url`. So the only thing preventing a working configuration was dao-ai's own check; the validator had no other job and is deleted rather than left empty.

  Three caveats are **documented rather than enforced**. The pairing is genuinely useful for a single tool-free agent, and the limits below are properties of specific models and of the gateway's current translation layer rather than of the configuration, so a static validator would have to reject working setups to catch them. First, and the sharpest: **a tool call fails on every model.** The gateway's `/responses` translator cannot deserialize a `function_call` content item, and returns `INVALID_PARAMETER_VALUE: Failed to parse ContentItem ... Could not resolve type id 'function_call'`. Observed live on a deployed app using `system.ai.gpt-5-4-mini`, a model whose `usage` block is complete, so it is independent of the next caveat. Every supervisor and swarm handoff is a tool call, as is every `tools:` entry, so in practice reserve the pairing for a single agent that calls nothing; `/chat/completions` handles tool calls normally. Second, whether a `/responses` reply *parses* depends on its `usage` block: OpenAI-family models return `input_tokens_details`/`output_tokens_details` and work end to end, while `gpt-oss-120b` and `claude-sonnet-4-5` omit both on every path — langchain-openai maps the absent fields to `None`, `AIMessage` rejects `None` there, and the reply raises `ValidationError` on `usage_metadata`. Use `/chat/completions` for those models. That is a client-side limitation, not a gateway one. Third, the gateway addresses only Foundation Model and UC-securable models, so a **custom ResponsesAgent endpoint** answers `404 "'<name>' does not exist."` through it — reach one with `use_responses_api: true` and `use_ai_gateway: false`, which is the flag's original purpose and is unaffected.

  dao-ai continues to use `/ai-gateway/mlflow/v1` and only that base URL, for both chat completions and Responses. The gateway also exposes provider-specific passthroughs (`/ai-gateway/openai/v1` and equivalents), but each covers only the models its provider serves, so routing everything through one base URL keeps behavior consistent regardless of the vendor behind a given endpoint — `use_ai_gateway_native_api` stays deliberately unsurfaced in config. The standing OBO-plus-gateway caveat the deleted validator carried moved to the `chat_model_for_workspace_client` docstring, the OBO entry point. `docs/configuration-reference.md` and `docs/faq.md` now carry the full probe matrix; the same sections also described dao-ai building a `langchain_openai.ChatOpenAI` client and `ChatDatabricks` having no `base_url` override, both of which stopped being true when the implementation became `ChatUnityAIGateway(ChatDatabricks)`, and both are corrected.

- **BREAKING — A Genie tool's `include_example_questions` now defaults to `false` and is opt-in in every case.** The field was tri-state and its default was conditional on *another* field: unset appended the space's example questions only when the tool declared no `description` of its own. That coupling made the description a hidden switch — adding one silently deleted the block, removing one silently added it — and documenting the behavior took a six-row truth table. It is now a plain `bool` defaulting to `false`: the questions are appended when, and only when, you write `include_example_questions: true`, independent of how the base description text was chosen. The tri-state existed for one reason, and that reason is now moot: intent had to survive the deploy bake (Model Serving dumps with `exclude_none=True`, Apps ships rendered YAML, so `model_fields_set` does not round-trip), which a `None` sentinel carried as a *value* — but with an unconditional default there is nothing left to distinguish, since `false` **is** the absence and `true` is the only signal, and both travel as ordinary values. Practical effect: up to ten questions per Genie tool stop riding in every LLM call unasked, and nothing reaches the prompt surface that the config author did not write. Affected configs are Genie tools with **no** `description` whose room has `sample_questions` (or `example_sqls`) — add `include_example_questions: true` to keep the block. No shipped example is affected (all 31 `type: genie` tools under `examples/` declare a `description`, so none got the block before either); `examples/04_genie/genie_basic.yaml` now sets the flag to demonstrate the opt-in. The routing floor from the previous release is untouched — telling two description-less Genie tools apart comes from the space-`description` fallback, not from the questions. When a room has example questions and the flag is off, an `INFO` line names the space so the unused signal is discoverable; note `app.log_level` defaults to `WARNING`, so this is a debugging aid rather than an upgrade alarm. Passing `include_example_questions: null` is now a validation error. `make schema` regenerates the JSON schema accordingly.

- **BREAKING — Removed the `config-paths` notebook parameter; `config-path` is the only config input.** Every pipeline step notebook declared a `config-paths` dropdown populated by walking `../config`, and it made an *interactive* run impossible: `dbutils.widgets.dropdown` rejects an empty `choices` list, and `../config` exists only in the staged bundle layout (where `config/` is a sibling of `notebooks/`) — never in a repo checkout. So the notebook threw at *widget creation*, before the careful "config-path is empty" `ValueError` beneath it could run. And where the directory did exist the dropdown was pointless: the bundle stages exactly one config (`pipeline/bundle.py`) and the generated job only ever passes `config-path`. Each notebook now reads `config-path` alone and, when it is empty, raises a message naming both layouts — the staged `../config/<name>.yaml` and an absolute workspace path for a hand-run. Discovery is **not** kept as a silent fallback: it would load the first YAML it happened to find, which is the same guessing that caused this. `dao_ai.utils.find_config_files` existed solely to feed the dropdown and is **removed**; the three hand-copied `find_yaml_files_os_walk` variants in the top-level `notebooks/` are gone too (those *raised* `FileNotFoundError` on a missing directory, so those notebooks died even earlier). Real-world impact is near zero — the generated bundle never passed `config-paths`, and passing only `config-paths` was already broken interactively — but scripts that set it will now fail with an unknown-parameter error.

- **BREAKING — A warehouse auto-derived from a Genie room is now keyed `<room-key>_warehouse`.** It was `normalize_name("<room.name>_<warehouse_id>")`, which produced churny keys like `my_genie_room_abc123def456` — and *raised `TypeError`* for a room declared by bare `space_id` with an inline `warehouse:`, because `name` is `None` until resolution runs, so such a config failed at parse time. The `genie_rooms:` mapping key is stable and always present. The `_warehouse` suffix is load-bearing rather than cosmetic: a warehouse key and a Genie room key both become an App resource *name*, and the DABs bundle has no uniquify pass, so a bare room key emitted two resources called e.g. `retail_genie` — one genie-space, one sql-warehouse — leaving the `value_from` env bindings ambiguous about which one they meant. It also matches the name `_extract_genie_warehouse_resources` has always given the same warehouse, so when both paths emit it the existing dedupe-by-identity pass collapses them. If a warehouse or Genie room already owns that key, the old `<room>_<warehouse_id>` form is used instead, so nothing is clobbered. The key names a generated App resource and a `resources.warehouses` entry, so anything referring to the derived warehouse by its old key — a `value_from` binding, a `warehouse:` cross-reference — needs the new name; a hand-declared `resources.warehouses` key is unaffected.

- **BREAKING — `--mode mcp` is replaced by `--as-mcp`, a protocol modifier on `--mode apps`.** MCP is a *wire protocol*, not a hosting platform, so it no longer sits on the `--mode` axis. `ServingMode` mixed the two vocabulary levels: `model_serving` and `apps` name Databricks platforms while `mcp` named a protocol served **by** the Apps platform — and the code showed it, since `deploy_mcp_agent` and `deploy_apps_agent` both called the same `_deploy_app()` and the MCP bundle writer delegates to the Apps bundle helpers. `--mode` is now strictly the platform axis (`model_serving | apps`), keeping it distinct from `--target` (the DAB *environment*) and from `--as-mcp` (the protocol). Migration: `dao-ai agent <verb> --mode mcp` → `dao-ai agent <verb> --as-mcp` (the old spelling is an argparse "invalid choice"); `ServingMode.MCP` is removed → `config.deploy_agent(mode=ServingMode.APPS, as_mcp=True)`. `--as-mcp` is accepted on every verb of **both** the `agent` and `workflow` nouns, plus `monitor logs` and `trace link`/`grant`. The `mcp` utilities noun (`tools`/`inspect`/`call`) is unaffected.
- **BREAKING — MCP servers now deploy as `mcp-<app>` instead of `<app>`.** Previously `--mode apps` and `--mode mcp` derived the *same* Databricks App name, so deploying one silently **replaced** the other (their staging dirs were separated, but the App resource was not); the docs worked around this by telling you to hand-name your app `mcp-*`. dao-ai now applies the `mcp-` prefix automatically to the App name, the DAB bundle name, and the default MLflow experiment, so a chat App and an MCP server built from one config coexist with separate service principals and experiments. The prefix is idempotent — an `app.name` already starting with `mcp-` is not doubled. The prefix is also what Multi-Agent Supervisor pattern-matches when auto-discovering MCP-hosted Apps. The exposed MCP *tool* name still comes from the unprefixed `app.name`. Existing MCP deployments are re-created under the new name; remove the old App if you don't want it lingering.
- **Agent staging dirs now mirror the platform/protocol axes.** `agent/<app>/{apps,mcp,ms}` becomes `agent/<app>/apps/chat`, `agent/<app>/apps/mcp`, and `agent/<app>/model_serving` — the protocol nests *under* the platform instead of sitting beside it, and `model_serving` is spelled out rather than abbreviated `ms`. `workflow/<app>` is unchanged (its bundle is mode-agnostic). Isolation guarantees are unchanged. Previously staged dirs are orphaned and simply rebuild on the next `build`/`up`; delete `.dao-ai/bundle` to reclaim the space.
- **`AppModel.app_resource_name` is joined by `dao_ai.config.app_name_for(name, as_mcp=...)`** as the single source of truth for the deployed App name, replacing three inline copies of the lowercase/hyphenate normalization. The property remains for the chat-protocol name.

- **BREAKING — Renamed `AppConfig.deploy_agent(target=...)` → `deploy_agent(mode=...)`** (and the same on `ServiceProvider`/`DatabricksProvider.deploy_agent`). The parameter is a `ServingMode` (`MODEL_SERVING`/`APPS`) and the CLI already exposes it as `--mode`; the method parameter now matches the type and the flag. Update any programmatic callers using the `target=` keyword: `config.deploy_agent(mode=ServingMode.APPS)`. Unrelated `target` names (DAB bundle targets, Vector Search `target_qps`, handoff `targets`) are unchanged.
- **BREAKING — Removed `PromptModel.schema` and `PromptModel.tags`** (and the derived `full_name` property). These were vestiges of the removed MLflow Prompt Registry — a UC-qualified name and metadata tags only mattered for a *registered* prompt, and inline prompts never register. `PromptModel` now carries only `name`, `description`, and `template` (plus the `jinja_template` property). Remove `schema:`/`tags:` keys from any `prompts:` block in your config; `make schema` regenerates the JSON schema accordingly.

### Removed

- **Removed the unused `get_resource_env_mappings()`.** It has been dead since the initial commit: nothing in `src/`, `tests/`, `docs/`, `examples/` or `notebooks/` ever called it, and it is not in `dao_ai.apps.__all__`. Worse than merely unused, it was misleading — it described a `valueFrom` env-var convention (`<KEY>_WAREHOUSE_ID`, `<KEY>_ENDPOINT`, `<KEY>_SPACE_ID`, `<KEY>_INDEX`, `<KEY>_DATABASE`) that no deploy path has ever generated. `generate_app_yaml` emits only the chat-UI proxy vars and MLflow's `MLFLOW_EXPERIMENT_ID` / `MLFLOW_TRACING_SQL_WAREHOUSE_ID`, so the function read as documentation of a scheme that does not exist and invited reasoning about resource keys as though they were env-var names.

### Fixed

- **A Databricks Apps deploy no longer fails outright when a model is named by its UC-securable id.** Apps validates its declared resources eagerly, so a three-level model name reached `POST /api/2.0/apps` as a `serving-endpoint` resource and aborted the deploy with `ResourceDoesNotExist: Endpoint with name 'system.ai.claude-sonnet-4-5' does not exist.` The short spelling would have been worse than the hard failure: `schema: *system_ai` + `name: claude-sonnet-4-5` declared a resource called `claude-sonnet-4-5`, which for someone whose workspace has an unrelated custom endpoint by that name would silently grant the app service principal `CAN_QUERY` on the wrong thing. Apps builds its resource list through **two** independent extractors and both had the bug — `_extract_llm_resources` (raw dicts, used by `generate_app_resources`) and `_extract_sdk_llm_resources` (SDK `AppResource` objects, the path `_deploy_app` actually takes) — so fixing only the first left the deploy failing identically; both are now pinned by tests. The rule they share now lives on the model as `InferenceEndpointModel.is_uc_securable` rather than being spelled out per call site. `_grant_serving_endpoint` needed no change: it already skips quietly when a name does not resolve.

- **The agent build log no longer names a different model than the one the request carries.** `create_agent_node` logged `agent.model.name`, which *was* the id sent to the serving layer until UC-securable names existed; a schema-qualified model logged the short segment (`claude-sonnet-4-5`) while calling `system.ai.claude-sonnet-4-5`. This is the only build-time record of which model an agent is wired to, so a log naming a different securable than the request sends anyone debugging a 404 or a grant to the wrong place — exactly the failure mode above. It now logs `full_name` for an `InferenceEndpointModel`, verified in a deployed app's container logs (`agent=charlie | model=system.ai.claude-sonnet-4-5`), and is unchanged for every model without a schema.

- **The OBO and agent-endpoint debug logs and trace resource attributes now name `full_name`, not the short segment.** The same divergence the agent build log had (above) lived in `OBOModelMiddleware`, the instructed-retriever decomposition client, and the agent-endpoint tool: each logged and set `ResourceInfo(..., model.name)`, so a schema-qualified OBO model traced `claude-sonnet-4-5` while invoking `system.ai.claude-sonnet-4-5`. All now use `full_name`, which is unchanged for every model without a schema.

- **A UC-securable model given as a bare `fallbacks` or `best_of_n.judge` string no longer fails at graph build.** String shorthand is promoted to an `InferenceEndpointModel`, and the promotion dropped `use_ai_gateway` — so `fallbacks: [system.ai.claude-sonnet-4-5]` loaded cleanly, then raised `ValueError` from `validate_schema_qualification` the moment `as_chat_model()` ran. A promoted string now **inherits the primary's `use_ai_gateway`**, so a fallback/judge routes the same way as the model it backs: a UC-securable name resolves through the gateway instead of crashing, and a plain endpoint name behaves exactly as before. This ends the previous "gateway primary, legacy-path string fallback" behavior — spell a fallback as a full model with `use_ai_gateway: false` to keep it on the legacy path.

- **The AI Gateway example no longer provisions against the reserved `system` catalog.** `examples/01_getting_started/ai_gateway.yaml` declared its `system.ai` anchor under top-level `schemas:`, a map whose entries are `CREATE SCHEMA`-provisioned and service-principal-granted at deploy — which fails or over-privileges on `system`. The schema is now inline on the model (not provisioned); a test guards that no shipped example declares a top-level schema in the `system` catalog.

- **A deployed agent no longer serves silently without its skills.** `SkillModel.as_middleware()` probed the filesystem *during pydantic validation* and baked the resolved absolute path into `MiddlewareModel.args["sources"]`, so the config carried the path of whatever machine happened to load it. On a Model Serving deploy driven from a job, that was the driver's ephemeral checkout — verified on a live deployment whose registered model contained `code/skills/<vertical>/<skill>/SKILL.md` while its logged config pointed the middleware at `/home/spark-928f77f1-.../.dao-ai/git/.../skills/<vertical>`, a directory that cannot exist in a serving container. Nothing failed: no exception, no dao-ai log line, endpoint healthy, agent quietly missing every skill it declared. Model Serving was the only target broken this way, because it alone rebuilds the config from a dict (`AppConfig(**ModelConfig().to_dict())`) rather than `from_file`, so it has no config path left to re-anchor against. The compounding detail was that `_translate_agent_skills_to_middleware` cleared `agent.skills` after translation while `rebase_relative_skill_sources` rewrote only `config.app.agents` at load time, so the shipped artifact held the same middleware three times with two different values. `as_middleware()` is now **pure** — it emits the config-relative parent directory and touches no disk — and resolution happens once, in `create_skills_middleware`, where the middleware is actually instantiated: that single site covers agent, sub-agent, deep_agent, and supervisor-level copies by construction, including the `swarm.default_agent`-shaped holder that the middleware walker used to skip. Anchors are tried in order — the config's own directory (when the config came from a local path), `$DAO_AI_PROJECT_ROOT`, the CWD, then each `sys.path` entry, which is what mlflow's `<model_dir>/code` prepend makes work — preferring an anchor that actually contains a `*/SKILL.md` over a same-named empty directory. Absolute sources still pass through verbatim, and `backend_type` other than `filesystem` (`state`, `store`, `volume`) skips resolution entirely, so `/Volumes/...` skills behave exactly as before. Because nothing is written back into the `AppConfig`, the `display_graph()`-then-`create_agent()` sequence in `07_deploy_agent.py` (and its two CLI equivalents) can no longer re-bake a driver path into the very next `model_dump()` — a regression test asserts the serialized config is byte-identical after building the middleware. `rebase_relative_skill_sources` is **removed**; it existed to patch the symptom and would now re-introduce it.

- **The MCP bundler, the workflow bundler, and the direct Apps deploy now stage local skill directories; previously they staged none.** Only the Apps *bundler* copied them. `dao-ai agent build --as-mcp` and the workflow DAB both wrote a config that named skills the bundle did not contain, so the reloaded config found no colocated `skills/` and the model shipped with zero skill content — a bug the pointer fix above cannot reach, because there is nothing on disk to point at. The copy logic is now shared (`stage_skill_dirs`), preserving the `skills/<vertical>/<skill>` layout that makes relative resolution work on the target: the MCP bundle stages at the bundle root (the server's CWD), and the workflow bundle stages under `config/skills/...` beside the staged config, which is what the step notebooks reload and what `collect_skills_code_paths` then hands to Model Serving. Already covered by the existing `config/**` sync glob, so no bundle-definition change is needed. The SDK-native Apps path (`deploy_agent(mode=APPS)`, `agent up --mode apps`) had the same hole for the same reason — it bypasses the bundler and uploads config, `code_paths`, and `src/` packages itself — and now uploads skill content beside the config in the app's workspace source, which is the app's CWD and therefore the anchor its relative sources resolve against. Verified live: the deployed app's workspace source contained `dao_ai.yaml`, `from_git_lib/`, `src/`, and `dist/` but no `skills/` at all, while its config named one.

- **A local `deep_agent.skills` entry no longer vanishes when the working directory is not the config's directory.** `resolve_skill_runtime_paths` accepted the `AppConfig` but never consulted it, resolving against `$DAO_AI_PROJECT_ROOT`, the CWD, and `sys.path` only. So `dao-ai run -c examples/13_orchestration/deep_agent_with_skills.yaml` from anywhere else — and every `from_git` notebook, where the checkout directory is by definition not the CWD — dropped the skill without a word. It now anchors on the config's directory first, passed explicitly rather than inherited ambiently so the function is correct when called directly.

- **An unresolvable local skill now fails the deploy instead of the agent.** `agent create`, `agent build`, `agent build --as-mcp`, the workflow bundler, and the direct Apps deploy each check every declared local skill and refuse to proceed, naming the target and each skill they could not find — a human is in the loop there, and shipping is the last moment to catch it. At runtime the same miss is a `WARNING` naming the source and every anchor tried, and the agent serves without that skill: raising in the container would turn a degraded agent into an endpoint that will not come up. **This will surface configs that are silently skill-less today** — if a deploy starts failing on a skill path, that path was not reaching the deployed agent before either. Skills on a Databricks FUSE mount — `/Volumes`, `/Workspace`, or `/dbfs` — are never flagged, since those are mounted inside Databricks compute and absent from the machine running the deploy, so whether the path exists locally says nothing about whether it will be there at runtime. Only `/Volumes` was exempt at first, which failed the deploy for a perfectly good `/Workspace/Shared/skills` that would have loaded fine; the set now comes from the same `_FUSE_ROOTS` the git-source loader uses, and matches per path segment, so `/Volumesnotreally/x` is still checked.

  The gate and the collectors only consider a skills middleware whose `backend_type` is `filesystem` — the factory's default is `state`, and under `state`, `store`, and `volume` a "source" is a key into graph state, a LangGraph Store namespace, or a volume path, none of which is expected on the deploying machine's disk. Checking them anyway made the gate contradict the runtime it exists to protect: `examples/12_middleware/deepagents_middleware.yaml` declares `sources: [/skills/base/, /skills/user/]` with no `backend_type`, and every deploy path refused a shipped example that serves correctly.

- **A config loaded from a URL is now rejected for relative *skill* paths, which its own guard already claimed to cover.** `_reject_relative_assets_for_remote_config` documented skills as one of the two fields that matter for security reasons, but its body checked only `datasets[].ddl`/`data`, `unity_catalog_functions[].ddl`, and `app.code_paths`. A remote config has no directory to anchor a relative path to, so `path: skills/research` would resolve against whatever local tree the process happened to be standing in and splice that Markdown into the agent's system prompt — a document that is explicitly not trusted to name local files, naming local files. Both the translated agent-level middleware `sources` and the untranslated `deep_agent`/subagent entries are checked, in **either** spelling: a bare string (`skills: [skills/research]`) is read the same way the resolver reads it — as a key into `resources.skills` when one matches, and as an inline relative path otherwise — because checking only the `SkillModel` form left the shorter spelling as a way straight past the guard. Volume-backed skills are unaffected: their paths are absolute and name nothing on the local disk, which makes them the right way to ship skills alongside a remotely-hosted config.

- **A declared `root_dir` on a skills middleware is now the first place a relative source is looked for.** Resolution consulted `$DAO_AI_PROJECT_ROOT`, the CWD, and `sys.path` but never the `root_dir` of the very backend it was configuring — so a hand-written `backend_type: filesystem` with `root_dir: /workspace/skills_root` and `sources: [skills]` latched onto whatever same-named directory happened to sit under the CWD instead. That made resolving *worse* than the pass-through it replaced, since the backend would have resolved the source under `root_dir` correctly. The declared root now leads the anchor list without replacing it, so a source that only exists under the CWD still resolves. `root_dir: /` is excluded, because it is not a declared root: it is the placeholder `SkillModel.as_middleware` emits for a config-relative source, and honoring it would anchor every source at the filesystem root — where a source of `.` resolves to `/` itself.

- **Skills declared only on a sub-agent now get a filesystem backend too.** The gate that upgrades from deepagents' default `StateBackend` read `deep_agent.skills` alone, so a config whose skills all live under `subagents[].skills` was served with a backend that reads from graph state — and those skills could not be loaded by any path, however correct. No exception and no log line, the same silent degradation as the pointer bug. The decision now reads the resolved sub-agent list, so it asks exactly what `create_deep_agent` receives, and the regression test asserts on the `backend` actually handed to deepagents rather than re-deriving the condition.

- **The logs now say whether skills loaded, which is the question the two bugs above make people ask.** Found by validating a sub-agent-only config on a live Model Serving endpoint: the skill demonstrably loaded — the trace's `SkillsMiddleware.before_agent` span reported it resolved to `/model/code/skills/...` — while the only relevant log line read `skills_count=0`, because `skills_count` counted `deep_agent.skills` alone. An operator grepping endpoint logs would have concluded the opposite of the truth. Three gaps, all silent on the happy path: the count ignored sub-agent skills, `_resolve_backend` logged nothing when it swapped deepagents' `StateBackend` for a `FilesystemBackend` (the single decision that determines whether a skill can load at all), and `resolve_skill_runtime_paths` logged only on a *miss*, so a successful resolution never named the directory it picked. `Creating deep_agent graph` now also reports `subagent_skills_count` and `instruction_files_count`, the backend swap is an `INFO` with its reason, and each resolved skill is logged with the directory it resolved to inside the container. Only `SubAgentModel` skills are counted, because `_agent_to_subagent` does not carry an `AgentModel`'s skills into deepagents, so those genuinely never load.

- **A `deep_agent.instruction_files` entry now reaches the deployed agent; before, none of them did.** The field is dao-ai's name for deepagents' `memory=` — `AGENTS.md`-style files whose contents are spliced straight into the system prompt — and it travelled the same road as `skills` while getting none of the same treatment. The relative string was passed to `create_deep_agent` verbatim, so it resolved against `FilesystemBackend`'s anchor, which with no `root_dir` is the **process CWD** — correct only when the process happened to start in the config's directory, and never true in a serving container, an Apps container, or a `dao-ai run -c examples/...` from the repo root. The failure is completely silent by construction: `MemoryMiddleware.before_agent` calls `download_files`, skips every source whose response is `file_not_found`, and renders `(No memory loaded)` into the prompt — no exception, no log line, and nothing in the prompt to indicate that instructions the config declared are missing. Entries are now resolved at graph build against the same four anchors skills use (the config's own directory, `$DAO_AI_PROJECT_ROOT`, the CWD, then each `sys.path` entry, which is what covers mlflow's `<model_dir>/code` prepend), through a separate file-shaped resolver: the predicate is `is_file()`, not `exists()`, because a directory satisfies `exists()` and is then dropped by `MemoryMiddleware` without a word. Absolute entries pass through verbatim, resolution is never written back into the `AppConfig`, and a miss at runtime is a `WARNING` naming the entry and every anchor tried while the agent serves without it — the same warn-at-serve, fail-at-deploy split as skills. Related: declaring `instruction_files` with **no** skills now forces the default backend to `FilesystemBackend`, which it did not before. That gap made such a config unfixable from the path side no matter what the path said, because deepagents' default `StateBackend` reads from graph state and never touches a disk.

- **Every bundler and the direct Apps deploy now stage instruction files; previously not one of them did.** The Apps bundler, the MCP bundler, the workflow DAB (under `config/`, beside the staged config the step notebooks reload), and the SDK-native Apps upload each ship them now, and Model Serving carries them in `code_paths`. What hid this for so long is that the canonical example's instruction file lives *inside* a skill directory, so skill staging carried it by accident — the one shape that works masked the fact that nothing staged instruction files at all. Because that shape is also the natural one, staging de-duplicates against the skill destinations rather than copying twice or reporting a file it had just written as skipped. The `code_paths` entry is the entry's **top-level directory**, not the file: `log_model(code_paths=[file])` lands a file at `<model_dir>/code/<basename>` and destroys the directory components, so `instructions/AGENTS.md` would arrive as `code/AGENTS.md` and no longer match the path the config declares. An entry pointing outside the config's own tree is warned about and skipped rather than relocated — unlike `code_paths`, an instruction file is found by its declared path, so a copy parked somewhere else would be a silent lie.

- **An unresolvable instruction file now fails the deploy, and a remote config is rejected for declaring a relative one.** The existing skill gate covers both families under one name (`assert_skills_resolvable` → `assert_skill_assets_resolvable`) at all five call sites — `agent create`, `agent build`, `agent build --as-mcp`, the workflow bundler, and the direct Apps deploy — reporting each problem by entry, because a second parallel gate beside a misleadingly-named first one is how the next asset type gets forgotten. `_reject_relative_assets_for_remote_config` now also covers `deep_agent.instruction_files`, closing the same hole it had for skills and for the same reason: a remote config has no directory to anchor against, so a relative entry would resolve against whatever local tree the process was standing in and splice that Markdown into the system prompt. Only `/Volumes/...` entries are exempt from the gate, matching how skill directories are treated — an entry like `/Users/me/proj/instructions/AGENTS.md` is checked like any other, so a typo in it fails the deploy instead of shipping an agent that renders `(No memory loaded)`.

- **A deep agent's skills and instruction files no longer become unreadable when deepagents 0.7.0+ is installed, for every backend dao-ai builds itself.** The default backend was built as `FilesystemBackend()`, relying on `virtual_mode` defaulting to `False`. deepagents flipped that default to `True` in 0.7.0 — its deprecation notice announced the change for 0.6.0, but 0.6.x still defaults to `False`, so the break landed a minor release later than advertised — and under virtual mode every incoming path is reinterpreted as a *virtual* path anchored at `root_dir` — the leading slash stripped and the remainder joined underneath — so a correctly resolved `/app/src/instructions/AGENTS.md` is looked up at `<cwd>/app/src/instructions/AGENTS.md`, and a `/Volumes/...` skill is rejected outright as "outside root directory". Every path dao-ai's runtime resolvers produce is a *real* host path — a config directory, an mlflow artifact's `code` dir, a UC volume mount — so none of them were reachable, and the two families failed differently: skills logged a `path_not_found` load error, while instruction files failed in total silence and the agent answered as though no memory existed. Because `pyproject.toml` allows `deepagents>=0.5.7`, this bit on version resolution rather than on any config change: the committed `uv.lock` pins 0.6.12, where the old default still holds, and Model Serving is unaffected for the same reason (mlflow pins the logged environment exactly, `deepagents==0.6.12`), while a freshly locked Apps bundle resolved 0.7.5 and broke — the same config, the same code, a different transitive pin. Confirmed on a live Databricks App that reported `NO MEMORY LOADED` while its uploaded source contained the file and its installed wheel contained the fix. Both construction sites now state `virtual_mode` explicitly — never left to whichever deepagents resolved — which is accepted by every allowed version (0.5.7 takes it as `bool | None`) and additionally silences the 0.6.x deprecation warning. The *value* is now the caller's, not a constant: the asset-reading paths pass `False`, because the paths they hand the backend are real host paths, while `create_filesystem_middleware` — whose tools (`read_file`, `write_file`, `edit_file`, `glob`, `grep`) take their paths from **model output** — defaults to `True`, since declaring a `root_dir` reads as intent to confine them to it. Set it to `False` there if an agent genuinely needs paths outside the root. What virtual mode does and does not buy, stated precisely because the earlier wording here had it backwards: `True` blocks `..`/`~` traversal and rejects paths resolving outside `root_dir`, which is path-based confinement and *not* sandboxing or process isolation — it does not restrict what the container's own identity can reach by other means — while `False` is what deepagents itself describes as providing "no security even with `root_dir` set". Write guardrails are unchanged either way: `deep_agent.permissions` and human-in-the-loop interrupts still apply. A regression test asserts the flag is passed at the call site rather than reading it back off the instance, since an attribute check passes on the pinned version whether or not the bug is present.

  One case is out of reach of the fix and is now loud instead: a config that names its own backend (`orchestration.deep_agent.backend: {name: deepagents.backends.FilesystemBackend}`) without `virtual_mode` in `args` still inherits the installed version's default, because overriding a value the user wrote by hand would be worse than telling them. That config now logs a `WARNING` naming both defaults and which one dao-ai's resolvers need.

- **Declaring `instruction_files` also changes which files a deep agent's *tools* can reach, where before it changed nothing.** Forcing the default backend to `FilesystemBackend` is what makes an `AGENTS.md` loadable at all (see above), but `deepagents.graph` appends a `FilesystemMiddleware` over that same backend unconditionally, so the model-facing `read_file`/`write_file`/`edit_file`/`glob`/`grep` tools move from `StateBackend` — ephemeral graph state, no disk — to the real filesystem, rooted at the process CWD. That is inherent to needing disk access, not a choice this change makes, and it is the same surface a config with `skills` has always had; it is called out because a config that declared only `instruction_files` did not have it before. Writes remain gated by `deep_agent.permissions` and human-in-the-loop interrupts, and a config that wants the tools confined can declare `backend` explicitly with `virtual_mode: true` and a `root_dir`.

- **A Genie-derived warehouse key no longer overflows the Databricks Apps resource-name limit.** `_extract_warehouse_resources` emitted the `resources.warehouses` dict key verbatim as the App resource `name`, unlike `_extract_table_resources`/`_extract_function_resources`, which route it through `_unique_resource_name` precisely because Apps enforces a 2–30 character rule. It did not bite while a warehouse could only be hand-declared, but a warehouse derived from a Genie room is keyed `<room-key>_warehouse`, spending 10 characters before the room key counts — so a room keyed `retail_inventory_genie` produced a 32-char name and a 400 `INVALID_PARAMETER_VALUE` on deploy. Now sanitized and uniquified like its siblings. Names already within the limit are unchanged; a key containing `.` or `-` is normalized to `_`, which can rename that App resource.

- **Every generated App resource name now obeys the 2–30 character rule, and no two can collide.** Fixing the warehouse extractor above one-at-a-time left the same latent 400 in seven of the twelve extractors `generate_app_resources` calls — `llm`, `vector_search`, `genie`, `genie_warehouse`, `volume`, `connection`, and `app` all emitted their `resources.*` mapping key verbatim as the resource `name`, so a Genie room keyed `retail_inventory_genie_room_for_the_stores` produced a 43-character name and the same `INVALID_PARAMETER_VALUE` on deploy. Per-extractor sanitizing would not have been enough: each extractor's `used` set sees only its own type, and this path — unlike `generate_deployment_resources` — has no uniquify pass of its own, so two *different* types that sanitize to the same 30 characters shipped two identically-named App resources and left any `value_from` binding ambiguous about which it meant. That collision is not hypothetical: a secret resource is named `<scope>_<key>`, so a warehouse keyed after the same scope/secret pair (`sc_wh`) collided with it before this change. `generate_app_resources` now normalizes the assembled list once, against a single shared set, which fixes all seven at once and covers any extractor added later. Resources are walked in extraction order, so the first emitter of a name keeps it and later ones take a numeric suffix within the length budget — warehouses are extracted before Genie rooms, so an over-long room key leaves the genie-space resource as the `_1`. The per-type `used` sets stay, since the extractors remain individually callable. Caveat, widened from warehouses to every resource type: a name already within the limit is untouched, but a key longer than 30 characters or containing `.`/`-` is normalized, which renames that App resource — anything referring to it by its old name needs updating.

- **A Genie room that references an existing space now contributes its SQL warehouse, so the first Genie question no longer 500s.** `ResourcesModel.update_genie_warehouses` is a `mode="after"` validator, and it called `genie_room.warehouse or genie_room.discover_warehouse()` — but discovery goes through `_get_space_details`, which returns `None` while `not self._resolved`, and rooms are resolved later. So auto-discovery was dead code: a room declared by `space_id` with no inline `warehouse:` — the common shape, since Genie titles are not unique — contributed no warehouse, the deployed app's service principal never got `CAN_USE` on it, and the first question through that room failed with a 500. The body moved to a reusable `ResourcesModel.backfill_genie_warehouses()`, called a second time at the tail of `AppConfig._resolve_all_resources()` — the choke point every deploy path funnels through, `initialize()` included but also the CLI paths that load with `initialize=False` and resolve by hand (`agent up --mode apps`, `--direct`, `agent build`, `service-principal grant -c`), which is exactly the set that needs the grant. Every consumer sits downstream of it: the SP grant plan's `CAN_USE` grant, the Model Serving auth policy, and the generated App resource list. The validator stays (correct for inline warehouses, and needs no network). An inline `warehouse:` is registered before any of the gates — it is a declaration, not a lookup — so a second room over an already-seen `space_id` keeps its explicit warehouse, and an `on_behalf_of_user` room keeps one too: OBO warehouses have to reach `resources.warehouses` for `generate_user_api_scopes` to emit the `sql` scope the forwarded user token needs. Only *discovery* skips OBO rooms, since the app SP is never granted `CAN_USE` on the caller's behalf. Discovery otherwise fires at most once per distinct `space_id` **per identity** — the cache is keyed on both, because a room may carry its own `service_principal`/`client_id`/`pat`, so one room's 403 must not suppress a later room whose credentials can read the same space — and it is recorded only *after* a lookup succeeds, so a failure never claims the space. It never raises: a space the deploying identity cannot read leaves the config exactly as written. A successful discovery is also written back to `genie_room.warehouse`, which makes the baked config self-describing and stops every fresh parse (Model Serving model load, Apps container startup) from re-issuing `get_space` + `warehouses.get` per room only to discard the answer at the dedupe check. Also hardened the resource layer beside it: `_extract_genie_warehouse_resources` was missing the `on_behalf_of_user` guard every sibling extractor has, and now has populated `genie.warehouse` data to act as the fallback it was written to be.
- **A Genie space with a long description no longer breaks the deployed app at startup.** `GenieRoomModel.description` is capped at 200 characters to match the Databricks Apps limit on `AppResource.description`, and the cap is enforced wherever a config is loaded — including inside the container. But the description back-filled by `ensure_resolved()` is *workspace* data, and nothing stops a Genie space description from being longer. Both deploy paths write that resolved value back into a config the container re-validates (Model Serving through the logged `model_config`, Apps through the baked YAML), so a 200+ character space description passed at deploy time and then failed the identical cap at startup with pydantic's `string_too_long` — before the app served a single request. A discovered description is now clipped to the limit (ellipsis-marked) at the one point it is adopted, which covers both paths; a description the *author* wrote is still rejected outright, since that one is theirs to shorten.
- **`workflow up --mode apps` now bakes Genie room details into the config it uploads, like `agent up --mode apps` already did.** `_bake_genie_room_details` had exactly one call site, the DABs App-bundle writer, so the SDK deploy path shipped the config text unbaked and silently lost the room's **`sample_questions`** — the few-shot routing hints a tool appends with `include_example_questions: true`, and the questions a room writes back into its space when it provisions one. `name` and `description` survived (the container's `ensure_resolved` back-fills those under `CAN_RUN`) but the questions come out of the serialized space payload, which needs `CAN_EDIT` — a permission a deployed app service principal does not hold — so deploy time is the only time they can be captured at all. `_deploy_app`'s config selection is now a small `_app_config_content()` helper, and both of its *text* shapes — the `params=`-substituted `rendered_yaml` and a raw `source_config_path` read off disk — get the bake; the third shape, a programmatically built `AppConfig`, needs nothing because it dumps objects `initialize()` already resolved with the deployer's credentials. Best-effort throughout: a bake failure or a file that will not decode as UTF-8 uploads the original bytes rather than blocking the deploy.
- **The top-level `notebooks/` demos install their dependencies again.** Six of the seven began with `%pip install --upgrade -r ../requirements.txt`, but `requirements.txt` was deleted in `d88c0c53` and the notebooks were never updated — so they failed in cell 1, before anything else could run. Each now uses the same bootstrap as the pipeline step notebooks: the newest `../dist/dao_ai-*.whl` if one is there, else the published PyPI package (`notebooks/../dist` is the repo-root `dist/`, exactly where `uv build` writes the wheel). dao-ai carries `python-dotenv` and `nest-asyncio` as core dependencies, so nothing else was lost; `03_optimize_context_aware_genie_cache` additionally installs `optuna`, which its tuning study is the only user of. A comment on each notes that an interactive run with no `../dist` wheel picks up the *published* dao-ai rather than your working tree, because that has bitten people. Found while fixing this: `06_background_agents` installed only the HTTP clients, so its optional "deploy the app first" cell raised `ImportError` on `dao_ai.config` — it now installs dao-ai too — plain, not `[all]`, because the demo's default path (`deploy_app=false`) never imports `dao_ai` at all and the config its deploy path builds (`18_background_agents/background_research.yaml`) is a prompt-only agent with no tools, so pulling every optional extra cost every run minutes for nothing. The three notebooks with a `config-path` widget also gained a real `defaultValue` pointing at a shipped example, matching what `07_feedback_demo` already did.
- **Notebook bootstraps pick the newest `../dist` wheel by version, not by filename.** All 22 wheel-selection cells (7 repo demos + 10 packaged step notebooks, five of which glob twice for a force-reinstall) sorted `glob.glob("../dist/dao_ai-*.whl")` lexically, so a stale wheel wins the moment the minor version reaches double digits — `0.2.8` sorts above `0.2.10` — and an interactive run silently tests the wrong build. Each now sorts on `packaging.version.Version` of the filename's version field, which also orders a dev wheel's `+local` tag correctly. Since a notebook cell is its own execution unit, the helper and its imports sit in every cell that globs; guard tests in `test_repo_notebooks.py` and `test_pipeline_bundle.py` assert both.
- **`01_run_examples` no longer dies at the `example-project` dropdown.** The cell that picks an inference example listed `examples/99_complete_applications/*/examples.yaml` straight into `dbutils.widgets.dropdown` — the same trap `config-path` had: `Path.iterdir()` raises `FileNotFoundError` when the directory is absent (uploading the notebook alone rather than the repo) and `dropdown` rejects an empty `choices` list, so the crash landed at *widget creation* with a bare traceback. Both cases are now caught before the widget, with a message saying what to upload and noting that the agent built in the cells above is already usable without the examples tree. The nested `example` dropdown is likewise skipped when an `examples.yaml` carries no `examples:` block.
- **The caller's OBO bearer token is no longer echoed back in responses or error text (security).** `dao_ai.apps.handlers._inject_headers_into_request` injects the *entire* inbound header map onto the runtime `Context` so tools can act as the calling user — including the live bearer in `x-forwarded-access-token`. Two outbound paths then serialized that context back toward the caller: `custom_outputs.configurable.headers` on every successful `predict`/`predict_stream`, and — worse — the "copy-paste this config" JSON block inside the user-facing `ValueError` raised by the `user_id`/`thread_id`/custom-field validation middleware, which lands in assistant message text and from there in the MLflow trace and any saved transcript. Both now route `configurable` extras through one shared filter, `dao_ai.state.context_configurable_fields`, which drops the declared `headers`/`user_id`/`thread_id` fields plus any extra whose *name* is credential-shaped (`authorization`, `api_key`, `session_cookie`, …) — `Context` is `extra="allow"` by design, so a caller can otherwise smuggle a secret in through the extras channel. Benign extras such as `store_num` still round-trip, so the block remains usable as the next request's `custom_inputs`. Headers are untouched **inbound**: OBO authentication and the `x-forwarded-user` → `user_id` fallback both still work. Nothing in-repo or in the chat UI read `custom_outputs.configurable.headers`, so this is behavioral only — no API contract changes and the config schema is unchanged. The name test lives in `dao_ai.diagnostics.is_secret_field_name`, which matches whole words rather than substrings, so `api_key`/`apiKey`/`x-forwarded-access-token` are filtered while `session_id` and `monkey_wrench` still round-trip; the substring matcher (`is_secret_key`) stays for env-var dumps, where over-redacting is free. A required custom field the caller *did* supply but whose name is credential-shaped is no longer replaced with its `example_value` in the copy-paste block — that told callers to paste `sk-proj-xxxxxxxxxxxxx` over a key they had already sent correctly — and is marked "keep the value you already sent" instead. The same bearer also reached the **MLflow trace**, because `_inject_headers_into_request` mutates the request before the `@mlflow.trace`-decorated `apredict`, so the span serialized it as an input attribute; `dao_ai._tracing.install_trace_redaction` now registers an MLflow span processor in the Apps, Model Serving and MCP entry points that replaces credential-shaped entries with `<redacted>` in span inputs and outputs, leaving the rest of the payload (including benign headers such as `x-forwarded-user`) intact for debugging.
- **Portable Apps bundle lock now rewrites every internal mirror host, not just `.dev.`.** `dao_ai._locking` hardcoded `pypi-proxy.dev.databricks.com`, so workspaces whose mirror is `pypi-proxy.cloud.databricks.com` (or a regional `*.cloud.` variant) shipped a `uv.lock` with unreachable URLs and the Apps build failed at `uv sync` with 404s (e.g. `pyarrow`, `scikit-learn`). The rewrite now matches any `pypi-proxy*.databricks.com` host, with an independent survivor guard so a future regression still fails loudly rather than shipping an unresolvable lock.
- **Sync `predict()` / `predict_stream()` no longer crash in a running event loop (#272).** The `LanggraphResponsesAgent`/`BackgroundResponsesAgent`/`LanggraphChatModel` sync wrappers previously called bare `asyncio.run()` (or `get_event_loop().run_until_complete()`), which raised `RuntimeError: asyncio.run() cannot be called from a running event loop` inside notebooks/IPython — requiring a manual `nest_asyncio.apply()`. They now drive the async graph on a shared, lazily-created background event loop (`dao_ai._async.run_sync`/`iter_sync`) that works from any calling context (notebook, Model Serving worker, plain sync) without patching the caller's loop — so it is also uvloop-safe on Databricks Apps (which uses `apredict`/`apredict_stream` directly and never the sync bridge). Caller contextvars (MLflow active-span, request state) propagate across the thread hop and stay isolated per concurrent caller.

- **BREAKING — Renamed the bundle lifecycle verbs to plain-language names** on the `agent` and `workflow` nouns: `generate → build`, `deploy → sync`, `run → start`, `destroy → down` (`up` is unchanged). The DAB names misled newcomers — mainstream tooling makes "deploy" mean "make it live", but the dao-ai `deploy` verb only *synced* the bundle to the workspace and a separate `run` started it. The new names say what each step does: **`build`** the bundle artifact, **`sync`** it to the workspace (does not start it), **`start`** it (make the app live / run the job), **`up`** for all-in-one. The old verbs are **removed** — `dao-ai agent deploy` / `run` / `generate` / `destroy` (and the `workflow` equivalents) now exit with an argparse "invalid choice" error. Update scripts; see the migration table in `docs/cli-reference.md`. The underlying `databricks bundle deploy`/`run`/`destroy` subcommands, the `deploy_job` resource, and the `up` orchestration are unchanged; the `mcp` noun's `tools`/`inspect`/`call` verbs are unaffected. No aliases kept.
- **BREAKING — Renamed the bundle staging-dir flag `-o/--output-dir` → `-s/--staging-dir`** on every bundle verb (`build`/`up`/`sync`/`start`/`down` across the `agent`, `workflow`, and `mcp` nouns). The flag never wrote a one-shot output — it names a persistent, reused staging directory (`sync`/`start`/`down` act on the same dir without rebuilding), and every other reference to it already used "bundle"/"staging" vocabulary (`DAO_AI_BUNDLE_DIR`, `_resolve_bundle_dir`). `-o` is now free for genuine output flags (`graph -o FILE`, `trace create -o FORMAT`). No alias is kept — update any scripts using `-o`/`--output-dir` on bundle verbs. The `DAO_AI_BUNDLE_DIR` env var and default `<base>/<kind>/<app>` layout are unchanged.

### Fixed

- **`agent down --mode model_serving` no longer orphans the serving endpoint.** The model_serving bundle is a Lakeflow Job that manages only the `deploy_job`; the serving endpoint is created imperatively by the deploy-agent notebook, so `bundle destroy` alone removed the job and left the endpoint running (and billing). `down` now also deletes the endpoint (`serving_endpoints.delete`, best-effort — a missing endpoint is not an error), keeping the registered UC model + versions as a reusable artifact. ### Added

- **Run agents and workflows straight from a git repository.** `--config` (and `AppConfig.from_git`) now accepts a git locator, so a dao-ai project that isn't on your machine runs like one that is:

  ```bash
  dao-ai agent up -c 'git+https://github.com/org/repo@v1.0#examples/retail/agent.yaml' -p my-profile
  dao-ai agent up --from 'gh:org/repo@v1.0' -c examples/retail/agent.yaml -p my-profile
  ```

  The recently-added URL support only ever worked for a *single self-contained* YAML: with no directory behind a URL there is nothing to anchor relative paths to, so a config declaring `ddl: data/products.sql` was rejected outright — which excluded most real projects. A git locator materializes the whole tree into a local cache and hands the loader a real path inside it, so every colocated-asset convention (`ddl`/`data`, `code_paths`, `src/`, `skills/`, `resources/`) resolves exactly as it does locally. No new dependency-declaration concept was needed: they all already anchor on the config's own directory.

  - **Grammar** follows pip/uv: `git+<scheme>://<host>/<owner>/<repo>[@<ref>][#<in-repo-path>]`, plus a `gh:owner/repo` shorthand. `@ref` takes a branch, tag, or full 40-character SHA; `#path` may name a file or a directory. Both are optional — omit the path (or point at a directory) and the config is discovered, preferring `dao-ai.yaml` and erroring with the candidates listed when ambiguous. Refs containing `/` (`@feature/foo`) work. Quote the locator: `#` starts a shell comment. In `--from` the `git+` prefix is **optional** — a browser URL (`https://github.com/org/repo@v1`) or an `scp`-style SSH reference (`git@github.com:org/repo.git`) is accepted, since `--from` can only mean a repository. In `--config` it is required, because there a plain `https://` URL means "fetch one YAML" and `git+https://` means "clone the tree".
  - **Caching** is per commit under `~/.dao-ai/git` (override: `$DAO_AI_GIT_CACHE`). A full SHA is immutable and never re-fetched; a branch or tag is re-resolved with `git ls-remote` each run and re-fetched only when it moved, so `up` on a branch always deploys current HEAD. An unreachable remote falls back to the newest cached checkout with a warning. New `dao-ai cache dir` / `cache clear [--repo LOCATOR | --bundles]` manage the space.
  - **Staging follows the config.** A local config still stages into the project-local `./.dao-ai/bundle` (unchanged). A git locator has no project directory to sit beside, so it stages into `~/.dao-ai/bundle/<repo>-<digest>/` — keyed by repository plus in-repo config path, so the same locator reuses one staging dir (and its idempotent-skip) regardless of the directory you run it from, and two projects that happen to name their app the same thing cannot collide. Previously a locator staged CWD-relative, so the same locator run from two directories built twice and neither saw the other's work. `$DAO_AI_BUNDLE_DIR` and `-s/--staging-dir` override as before. `~/.dao-ai` is deliberately not under `$XDG_CACHE_HOME`: a checkout is not disposable the way a cache is, and the name mirrors the project-local `.dao-ai/`.
  - **Auth** delegates to `git`, so ssh-agent and credential helpers work untouched. For headless use (notebook, CI) `DAO_AI_GIT_TOKEN` / `GITHUB_TOKEN` is passed via an inline credential helper — never interpolated into the remote URL (which would persist it in the cache's `.git/config`), never in argv, and redacted from errors. A locator carrying inline credentials is rejected with a pointer to the env var.
  - **Trust:** a git locator runs the repository's code, exactly as `git clone` + `dao-ai agent up` would. The resolved SHA is reported on every load. Pin a tag or SHA for repos you don't control.
  - Requires `git` on `PATH`. Resolution is client-side only — the generated bundle stays self-contained, so nothing needs `git` at deploy or run time.

  Alongside this, `AppConfig.from_*` was refactored onto a `ConfigSource` abstraction (`dao_ai.sources`): `FileSource` / `UrlSource` / `GitSource` each answer where the bytes come from and whether a local tree backs them, and `from_file` delegates to a single `from_source` implementation. Every `from_*` method now accepts either a spec string or an explicitly-constructed source (`AppConfig.from_git(GitSource(spec, token=..., refresh=True))`), differing only in the source type it pins — `from_file`/`from_source` are lenient, `from_url`/`from_git` validate. Behavior for existing local and URL configs is unchanged.

- **First-class `type: sql` tool + parameterized SQL statements against warehouse *and* Lakebase.** The SQL statement tool now accepts optional, typed bound parameters and can target either a SQL warehouse (`WarehouseModel`) or a Lakebase / Postgres database (`DatabaseModel`), dispatching on backend type. `dao_ai.tools.sql.create_execute_statement_tool` gains a `params: list[StatementParam]` argument and two public backend factories — `create_warehouse_statement_tool` / `create_lakebase_statement_tool`. Each `StatementParam` declares a `source` of `llm` (surfaced in the tool schema the model sees) or `context` (bound server-side from the runtime `Context`, hidden from the model); values are bound **natively** (`:name` for warehouse, `%(name)s` for Lakebase) — never string-interpolated, so both backends are injection-safe. A new first-class `SqlToolModel` (`type: sql`, with mutually-exclusive `warehouse:` / `database:` fields) is added to the `AnyTool` union alongside `genie` / `lakebase_search`, so the tool is declaratively configurable with typed fields; it inherits `human_in_the_loop` / `audit` / `call_limit` from the base tool model, so a mutating statement can be gated behind human approval with a signed audit receipt. OBO follows the existing `workspace_client_from(context)` pattern (warehouse OBO works on Model Serving and Apps); Lakebase Model-Serving OBO is honored today and a documented seam makes Apps OBO a one-line change once the shared pool threads request context. `params=None` preserves the legacy zero-argument tool. - **Diagnostic visibility for cache auth-mode resolution.** Two new structured log lines surface the root cause of the most common Postgres semantic-cache permission failure — operators configuring `DatabaseModel.client_id` but having the secret resolution silently fail back to ambient (App SP) auth. (1) `PostgresContextAwareGenieService._setup` now emits an INFO line `dao_ai.cache.auth.mode | mode=service_principal\|ambient | sp_client_id=...` at boot so operators can see at a glance whether the cache is connecting as the stable configured SP or as the App's auto-injected SP. (2) `IsDatabricksResource.workspace_client` now emits a WARNING `dao_ai.auth.client_id.unresolved` when `client_id` is configured in YAML but `value_of()` returns `None` (silent fallback) — naming the resource class + the scope/key the operator likely needs to grant the App SP `READ` on. - **MCP server for dao-ai tools, with one-command `dao-ai generate-mcp` deploy.** Any dao-ai config that defines `create_genie_toolkit` or `create_vector_search_tool` factories can now be exposed as a Model Context Protocol (MCP) server hosted on Databricks Apps — no agent runtime, no LangGraph, just the tools served over [Streamable HTTP](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports). Any MCP client (Claude Desktop, Cursor, agent platforms) can connect to a deployed app and call the tools natively.

  Highlights:
  - **New CLI subcommand `dao-ai generate-mcp`.** Mirrors `dao-ai generate-bundle` — reads an AppConfig, walks `config.tools`, and emits a deploy-ready Databricks Apps bundle (`databricks.yml` with `bundle.engine: direct`, `app.yaml`, `pyproject.toml`, `requirements.txt`, README) that runs the MCP server on Databricks Apps. Skips `agents:` / `app:` blocks entirely — the MCP server is tool-only. Supports `--development` (bundles a local dao-ai wheel + switches the generated pyproject to install from it; needed until 0.1.89+ is on PyPI).
  - **Pluggable adapter registry.** Tools are NOT hardcoded in the MCP server. Each dao-ai tool factory is exposed via its own adapter in `dao_ai/mcp/adapters/` that calls `register_adapter(McpAdapter(factory_name=..., register=...))` at import time. Two adapters ship: `genie` (rebuilds the `Genie → GenieService → PostgresContextAwareGenieService → LRUCacheService` chain and registers `<name>` + `<name>_feedback` MCP tools per `create_genie_toolkit` entry) and `vector_search` (invokes `create_vector_search_tool` and wraps its `StructuredTool` — inheriting hybrid + query decomposition + RRF + reranking + verifier). A new factory needs only a new adapter module — no edits to the MCP server core.
  - **Names and descriptions come from dao-ai.** The MCP server lifts each tool's `name` / `description` from the configured factory `args` (or from the LangChain tool object the factory returns), so what the LLM sees as a tool is what dao-ai's own factories advertise. No MCP-side string prefixes/suffixes.
  - **Streamable HTTP, stateless, single `/mcp/` endpoint.** `FastMCP(stateless_http=True, json_response=True, streamable_http_path="/")` mounted at `/mcp` on a FastAPI app, with the session manager driven by FastAPI's lifespan. Scales horizontally across Databricks Apps replicas with no sticky sessions. Blocking dao-ai calls run inside `asyncio.to_thread` so the event loop stays unblocked under concurrency.
  - **Rich `_meta` on every response.** `ask_<name>` returns SQL + result preview + `_meta.{cache_hit, served_by, latency_ms, message_id, cache_entry_id, conversation_id, trace_id, space_id, tool_name}`. `submit_feedback` and `<vs_tool>` return their own `_meta`. Honors client `_meta` on `tools/call` for `dao-ai/conversation_id` (multi-turn) and `dao-ai/disable_cache` (bypass).
  - **Auth.** Default is App SP via Databricks Apps' auto-injected `DATABRICKS_CLIENT_ID`/`DATABRICKS_CLIENT_SECRET`. The `x-forwarded-access-token` header is captured per-request and surfaced as `obo_present` in every loguru log line — OBO is wired through dao-ai's existing `IsDatabricksResource.on_behalf_of_user` flags (set per-resource for selective OBO).
  - **New `[mcp]` extra.** `pip install 'dao-ai[mcp]'` brings in `fastapi` + `uvicorn[standard]`. The core MCP SDK was already a dependency.
  - **New console script `dao-ai-mcp-server`.** Invoked by the generated `app.yaml` as `["uv", "run", "dao-ai-mcp-server"]`. Reads its config from `$DAO_AI_MCP_CONFIG_PATH` (the rendered dao-ai.yaml co-located in the bundle).
  - **Default Databricks App name is `mcp-dao-ai`** (overridable via `config.app.name`). The `mcp-` prefix is a discovery signal for Databricks Multi-Agent Supervisor (MAS), which pattern-matches it when enumerating MCP-hosted Apps across an account.
  - **Postgres semantic cache: multi-tenant guidance in docs.** The cache table is designed for multi-tenant use — rows are isolated by `genie_space_id`, so multiple Genie spaces and multiple MCP/agent deployments sharing one Lakebase project share one cache table (`genie_context_aware_cache` / `genie_prompt_history`). Verified on FEVM that two distinct Apps with distinct SPs (`mcp-sporting-goods` and `mcp-hardware-store`) both write to and read from the shared tables once the project owner has run a one-time `GRANT ... TO PUBLIC` on the table + sequence. Troubleshooting docs explain the exact GRANT statements and call out the underlying schema asymmetry (the cache tables' `SERIAL` PK introduces an implicit sequence with its own ACL; LangGraph's checkpointer sidesteps this by using composite text PKs — tracked as a follow-up improvement to migrate the cache tables to the same pattern).
  - **Example config.** `config/examples/15_complete_applications/sporting_goods_store_mcp.yaml` — a slim MCP-only flavor of the sporting-goods config; 2 Genie toolkits + 1 instructed VS retriever, no agents/app blocks. End-to-end tested against the FEVM workspace: LRU `cache_hit` progression demonstrated (`false → true(lru) → false-after-feedback-invalidates`), instructed retrieval pipeline confirmed firing (decomposition into 3 subqueries + RRF + fallback to standard search), App SP auth across Genie / VS index / Lakebase / SQL warehouse / serving endpoints.
  - **Docs.** New `docs/mcp_server.md` covers the wire shape, adapter registry, generator UX, deploy flow, troubleshooting, and the `_meta` contract.
  - **8 new unit tests** covering config loading, adapter dispatch, tool registration, and bundle generation.
  - **Schema unchanged.** No `config.py` Pydantic models were modified — `schemas/model_config_schema.json` does not need regeneration.

  This pairs with but is independent of the existing `dao_ai.apps.mcp` module, which provides primitives for *consuming* external MCP servers from a dao-ai agent (client-side). The new `dao_ai.mcp` package is the *server* side.

- **Google A2A (Agent2Agent) protocol support on Databricks Apps deployments.** Every dao-ai agent deployed to Databricks Apps now automatically exposes a fully [A2A v0.3](https://a2a-protocol.org)-compliant endpoint alongside the existing OpenAI Responses contract. Two new routes are mounted on the same FastAPI app:
  - `GET  /.well-known/agent-card.json` — public Agent Card discovery.
  - `POST /a2a`                          — A2A JSON-RPC 2.0 (`message/send`, `message/stream` over SSE, `tasks/get`, `tasks/list`, `tasks/cancel`, `tasks/subscribe`).

  Both protocols share one compiled LangGraph and one checkpointer, so conversations stay consistent across contracts. No config change is required to enable A2A — set `app.deployment_target: apps` and you're done. Opt out via `app.a2a.enabled: false`.

  Highlights:
  - **Agent Card auto-derivation.** Skills default to one `AgentSkill` per entry in `app.agents`. The `bearer` security scheme description is conditioned on `app.a2a.on_behalf_of_user` to advertise OBO support. The card `url` derives from `$DATABRICKS_APP_URL` at startup. Override any field via `app.a2a.skills` / `app.a2a.security_schemes` / `app.a2a.server_url`.
  - **HITL parity.** A LangGraph `interrupt()` raises a terminal `TaskStatusUpdateEvent(state=INPUT_REQUIRED)` with the interrupt payload as a `DataPart`. Clients resume by sending another `message/send` for the same `taskId`+`contextId` carrying either a structured `DataPart {"decisions": [...]}` (machine-to-machine) or a free-text `TextPart` (the existing dao-ai `handle_interrupt_response()` LLM parser handles it).
  - **OBO parity.** The Databricks Apps proxy's `x-forwarded-access-token` header is captured by a2a-sdk's `DefaultCallContextBuilder` and injected into `configurable.headers` so OBO tools see the end-user's token unchanged.
  - **Task persistence.** `app.a2a.task_store` is an `A2ATaskStoreModel { database, table }` — independent of `app.long_running`. No `database` → in-memory; set `database` → Lakebase persistence in the configured `table`. Share a connection pool with `LongRunningStore` and the LangGraph Postgres checkpointer by pointing all three at the same `DatabaseModel`; `AsyncPostgresPoolManager` dedupes by connection-string value.
  - **Typed security schemes.** `A2AModel.security_schemes` is typed against a2a-sdk's `SecurityScheme` discriminated union, so malformed schemes fail at config-load time. dao-ai ships ready-made constants and factories in `dao_ai.apps.a2a.security` (`BEARER_DATABRICKS_PAT`, `BEARER_DATABRICKS_M2M`, `BEARER_DATABRICKS_OBO`, `api_key_header`, `oauth2_databricks_authorization_code`, `oauth2_databricks_client_credentials`, `oauth2_databricks_obo`, `openid_connect_databricks`). YAML users can author the equivalents inline using `${workspace.host}` substitution.
  - **Auto-derived OBO advertisement.** `A2AModel.on_behalf_of_user` is now three-state (`Optional[bool]`, default `None`). With `None`, dao-ai scans the config for any `IsDatabricksResource` with `on_behalf_of_user: true` and auto-advertises OBO on the Agent Card. When effective OBO is True, the Agent Card emits **both** an `oauth2` scheme (the declarative authorization-code flow with `user_impersonation` scope, URLs from `$DATABRICKS_HOST`) and a `bearer` scheme (the wire shape); A2A clients pick the one their auth machinery supports. Users can pin `a2a.on_behalf_of_user: true|false` to override.
  - **Shared HITL helper.** Both the Responses path (`LanggraphResponsesAgent.apredict` / `apredict_stream`) and the A2A executor delegate to a new `dao_ai.hitl.decide_graph_turn`, eliminating ~150 lines of duplicated HITL decision logic.
  - **New config models.** `A2AModel`, `A2ASkillModel`, `A2ATaskStoreModel`. `A2AModel.on_behalf_of_user: bool` replaces the previously-proposed (unshipped) `AppModel.on_behalf_of_user` advisory flag — A2A's Agent Card was its only consumer. Per-resource `on_behalf_of_user` fields elsewhere (AgentModel, GenieRoomModel, VectorStoreModel, etc.) are unchanged. Schema regenerated.
  - **New `app.a2a` field on AppModel** (`Optional[A2AModel]`). Default `None` is treated as `A2AModel()` (enabled with sensible defaults).
  - **Worked examples.** `config/examples/20_a2a_protocol/a2a_minimal.yaml` (deploy-ready, dependency-free), `a2a_long_running.yaml` (Lakebase-persistent task store), and `a2a_hitl_obo.yaml` (HITL + OBO over A2A). `examples/a2a/client.py` is an end-to-end Python client that exercises the agent card, message/send, message/stream, and HITL resume flows.
  - **Docs.** New `docs/a2a_protocol.md` covers the wire-shape mappings, configuration surface, HITL/OBO semantics, task-store configuration, security-scheme recipes (Python + YAML), and spec-compliance scope.

  Model Serving deployments are unchanged — A2A is Apps-only because the MLflow Model Serving runtime cannot mount arbitrary FastAPI routes.

## [0.1.74]

### Changed
- **CLI: renamed `dao-ai bundle` to `dao-ai pipeline`** to disambiguate from the underlying Databricks Asset Bundle (DAB) feature it wraps. ### Added
- **Best-of-N + LLM-as-judge wrapper (`LLMModel.best_of_n`)**: opt-in primitive that fans out N parallel candidate generations on any configured `LLMModel` and asks a judge model to score them. The wrapper returns `candidates[argmax(scores)]` verbatim — never synthesised. Works as a drop-in `BaseChatModel`: every existing call site (agent nodes via `as_chat_model()`, OBO retrievers via `_get_cached_llm()`, structured-output classifiers like the verifier/router/reranker via a dedicated `with_structured_output` runnable) picks up the wrapping when `best_of_n: { n: 8, judge: <ref-or-name> }` is added to an LLM block. Diversity floor enforced (`max(LLMModel.temperature, 0.7)` unless overridden via `temperature_override`). Disables streaming when set. MLflow trace shape per invocation: one `best_of_n` parent CHAIN span (records `n`, `selected_index`, `scores`, `judge_reasoning` as attributes) + N `candidate_*` LLM child spans + one `judge` LLM child span. Hard cap `n ≤ 16`. Default `n = 8`. No shipped example enables it; opt in by adding the field to any `LLMModel` block.
- **Vector Search endpoint `target_qps` (Public Preview)**: New optional field on `VectorSearchEndpoint` that provisions target queries-per-second on STANDARD endpoints. Scales endpoint compute linearly (cost scales linearly too). Honored at endpoint-creation time only — if the endpoint already exists, the configured value is logged at debug level but not reconciled. Validated at config-load time: setting `target_qps` on an `OPTIMIZED_STORAGE` endpoint raises a `ValidationError`. Bumps `databricks-vectorsearch>=0.67` (which introduced the underlying `min_qps` SDK kwarg) and `databricks-sdk[openai]>=0.106.0`. See `docs/configuration-reference.md` for usage and constraints.
- **Swarm handoff constraints (`requires`)**: New optional field on the agent model declaring prerequisite agents that must have run before this agent can be reached via handoff. Enforced inside swarm handoff tools — when prereqs are unmet, the tool returns a refusal `ToolMessage` naming the missing agents and `active_agent` stays unchanged so the LLM can self-correct. Validated at config-build time (unknown agents, self-reference, cycles in the `requires` DAG, and deterministic handoffs to constrained targets are all rejected). Swarm-only in this release; supervisor adoption is planned. See `docs/architecture.md` → "Swarm Pattern" → "Handoff constraints" for details.

- **MCP Tool Filtering**: Control which tools are loaded from MCP servers
  - `include_tools`: Optional allowlist with glob pattern support (e.g., `["query_*", "list_*"]`)
  - `exclude_tools`: Optional denylist with glob pattern support (e.g., `["drop_*", "delete_*"]`)
  - Precedence: exclude always overrides include for maximum security
  - Pattern syntax: `*` (any chars), `?` (single char), `[abc]` (char set), `[!abc]` (negation)
  - Use cases: Security (block dangerous operations), performance (reduce context), access control
  - New example config: `config/examples/02_mcp/filtered_mcp.yaml` with 6 filtering strategies
  - Comprehensive documentation in configuration reference and MCP README

- **CLI: list-mcp-tools Command**: Discover and inspect MCP tools from configuration
  - Lists all available tools from configured MCP servers with full details
  - Shows tool descriptions (no truncation), parameters, types, and requirements
  - Pretty-printed schemas in readable format (53% more compact than JSON)
  - Filter statistics: total available, included, and excluded tool counts
  - `--apply-filters` flag: Show only tools that will be loaded (respects include/exclude)
  - Aggregated output: Collects all data before display (no logging interference)
  - Detailed exclusion reasons: Shows why tools are filtered out
  - Use cases: Discovery, debugging, validation, planning, documentation

- **AnyVariable Support for Additional Fields**: More configuration flexibility
  - `SchemaModel.catalog_name` and `SchemaModel.schema_name` now support AnyVariable
  - `DatabricksAppModel.url` now supports AnyVariable
  - Allows environment variables, Databricks secrets, and fallback chains
